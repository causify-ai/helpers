- This file contains conventions for C4 diagrams (Context, Container, Component,
  Code)

# Refresher for the Reader

## Open the Diagram Section with a C4 Refresher

- Put a short refresher of the C4 levels before the first diagram of the doc
  - Write it once per project, in `docs/02-design.architecture.md`
  - Do not repeat it in the component docs `docs/02.<N>-design.<component>.md`
- Keep it to about 15 lines, in a `### C4 Refresher` section under `## Diagram`
- Cover these points
  - The four levels, each with a one-line definition and the question it answers
    - **C1 (Context)**: the system as one box, with its users and the external
      systems around it. Question: who uses the system, and what does it depend on?
    - **C2 (Container)**: the parts of the system that run or store data on their
      own (e.g., app, service, script, DB), and how they call each other. Question:
      what is the system made of, and with which technology?
    - **C3 (Component)**: the parts inside one container (e.g., modules, classes).
      Question: how is one container organized?
    - **C4 (Code)**: the classes and functions inside one component. Not drawn: the
      code is the diagram
  - The element kinds: `Person`, `System`, `Container`, `Component`
    - `_Ext` marks what the team does not build
    - `Rel` is a labeled arrow: a call, an import, or a data flow
    - `Boundary` groups elements
  - Which levels this doc draws, and where the others live
- Each level zooms into one box of the level above: say so in the first bullet
- Example: `research/Estimate_academic_paper_quality/docs/02-design.architecture.md`

# Diagram Language

## Always Draw C4 Diagrams with PlantUML

- Draw every C4 diagram with PlantUML and the C4-PlantUML library, in a `plantuml`
  code fence
- Never draw a C4 diagram with Mermaid (`C4Context`, `C4Container`, `C4Component`)
  - Mermaid places C4 shapes on a fixed grid whose row width is capped at the screen
    width of the headless browser
  - PlantUML lays out the shapes from the relations, so the layers and the neighbors
    of a system stay close
- Mermaid is still valid for diagrams that are not C4 (e.g., mind maps), see
  `.claude/skills/figure.rules.md`
- Render the diagram with `render_images.py`, which handles the `plantuml` fence

## Start Every Diagram with the Same Header

- Write the three header lines in this order
  ```plantuml
  !pragma layout smetana
  !include <C4/C4_Container> 
  LAYOUT_TOP_DOWN()
  ```
- Do not write `@startuml` and `@enduml`: `render_images.py` adds them
- Keep `!pragma layout smetana`
  - The PlantUML Docker image has no Graphviz
  - Without the pragma the render fails with "Cannot find Graphviz"
- Include the C4 library with `!include <C4/C4_...>`, not with a URL
  - The library is bundled in `plantuml.jar`, so the include works offline
  - Use `<C4/C4_Context>`, `<C4/C4_Container>`, or `<C4/C4_Component>` for the level
    of the diagram
  - Each library includes the levels above it, so `Container_Ext` is available in a
    component diagram
- Pick the direction with `LAYOUT_TOP_DOWN()` or `LAYOUT_LEFT_RIGHT()`
  - Use `LAYOUT_TOP_DOWN()` for layers and call chains
  - Use `LAYOUT_LEFT_RIGHT()` for one central system with several neighbors

# Elements and Relations

## Use the C4-PlantUML Macros

- Use these macros, which have the same names and arguments as in Mermaid
  - `Person(id, "label", "description")`
  - `System(...)` and `System_Ext(...)` for a system and an external system
  - `Container(id, "label", "technology", "description")`, `Container_Ext(...)`, and
    `ContainerDb(...)`
  - `Component(...)` and `Component_Ext(...)`
  - `Container_Boundary(id, "label") { ... }` and `System_Boundary(...)`
  - `Rel(from, to, "label", "technology")`
- Indent the elements inside a boundary by 2 spaces
- Put the C4 level in the title, e.g., `title Estimate Paper Quality: Context`

## Fill the Technology Only for Mixed Technologies

- Fill the technology field only when the elements use different technologies
  - E.g., different languages, different DBs
- Leave the field empty when all the elements use the same technology
  - E.g., if everything is Python, do not write "Python CLI" or "Python module": the
    label says nothing
  - **Bad**
    ```plantuml
    Container(cli, "estimate_paper_quality.py", "Python CLI", "Parses args")
    Container(rater, "epq_rater.py", "Python module", "Rates a paper")
    ```
  - **Good** (all Python)
    ```plantuml
    Container(cli, "estimate_paper_quality.py", "", "Parses args")
    Container(rater, "epq_rater.py", "", "Rates a paper")
    ```
  - **Good** (mixed: label the elements that differ)
    ```plantuml
    Container(api, "api", "Python", "Serves the requests")
    Container(worker, "worker", "Go", "Runs the jobs")
    ContainerDb(db, "store", "PostgreSQL", "Keeps the jobs")
    ```

## Escape Creole Markup in Labels

- PlantUML reads `--text--` in a label as strikethrough
- Write `~-~-` for a literal `--`
  - **Bad** (renders `input, output_dir` with a line through `input,`)
    ```plantuml
    Rel(user, cli, "--input, --output_dir")
    ```
  - **Good**
    ```plantuml
    Rel(user, cli, "~-~-input, ~-~-output_dir")
    ```
- Write other label text as is: `<doi>`, `%PDF`, `lookup_*()`, and `_get()` render
  literally

# Verification

- [ ] A `### C4 Refresher` section comes before the first diagram of the project
- [ ] The refresher defines C1, C2, C3, and C4, and says which levels the doc draws
- [ ] The diagram is in a `plantuml` fence, not a `mermaid` fence
- [ ] The header has the three lines `!pragma layout smetana`, `!include
  <C4/C4_...>`, and a `LAYOUT_*()` line
- [ ] There is no `@startuml` or `@enduml`
- [ ] No label contains `--` without the escape `~-~-`
- [ ] The rendered image has no overlapping shapes or labels
